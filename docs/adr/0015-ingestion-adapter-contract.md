# 0015 — Ingestion adapter contract

Status: **Accepted** (2026-10-17). Written with plan 0011 (issue #7). Decisions 1 to 7 are technical and follow from ADRs 0003, 0009, 0011 and 0012. Diego approved decision 8 (competition and season taxonomy) on 2026-10-17, together with the two extra 2020 matches (stored with `is_final: false`).

## Context

`data/` is the single source of truth (CLAUDE.md), and every source approved in ADR 0003 (openfootball, API-Football, the Kaggle dataset, later RSSSF and Wikipedia) has its own format. Issue #7 asks for one adapter per source in `scripts/ingest/` that normalizes into the data model of ADR 0009, is deterministic, puts a `source` on every record, never overwrites `data/` with malformed or partial input, and is tested against recorded fixtures without network.

Several adapters will write into the same files (`matches.json`, `competitions.json`, `seasons.json`), and some records are shared between them (the Primera División competition is fed by openfootball from 2018-19 and by Kaggle before that). Without a common contract, two adapters could overwrite each other's records, produce different ids for the same match, or leave `data/` half written after a failure. ADR 0012 already fixes how a source team name becomes a club id; this ADR fixes the rest.

## Decision

1. **Shape.** Each source is one folder `scripts/ingest/<source>/` with a **pure core** (parse and normalize: no I/O, no clock, no network) and a thin I/O layer (fetch or read the input). Shared code lives in `scripts/ingest/core/`. Every adapter implements one interface: it declares its id, its owned `source` prefix and its reference records (competitions, seasons), loads its raw input through an injected loader, and returns normalized records plus a run report. `scripts/ingest/index.ts` is the only CLI (`pnpm data:ingest <adapter> [--dry-run] [--out <dir>] [--from <dir>]`).
2. **Pinned, verifiable input.** An adapter that reads a public repository or file pins the upstream revision (for GitHub, a commit SHA) and the `sha256` of every file it reads. A mismatch stops the run. Moving to a newer upstream revision is a normal data PR that changes the pin, the hashes and, therefore, the diff of `data/`. Every record's `source` is a permalink to that pinned revision (for openfootball, the file URL at the commit SHA plus the `#L<line>` anchor of the match line), so an auditor can open the exact text used.
3. **Ownership and merge.** An adapter **owns** the match records whose `source` starts with its source prefix; on each run it replaces all of them and touches nothing else. Reference records (competitions and seasons) come from the adapter's reviewed config and are **upserted by id**: added when missing, kept when deep-equal, and a **conflict** that stops the run when a record with the same id differs (a human checkpoint per CLAUDE.md, never resolved automatically). The same match from two sources is not merged: one source per match (ADR 0011, decision 6), and the existing `duplicate-match` rule catches an overlap.
4. **Write only valid data.** The adapter builds the complete next dataset in memory (existing `data/` plus its merged output), runs the same `validate()` used by `pnpm data:validate` plus the adapter's own source checks, and writes **only if there are zero issues**. Files are written to a temporary file in the same folder and renamed into place; all temporary files are written before the first rename, and files whose bytes would not change are not touched. A failed run leaves `data/` byte-for-byte unchanged and prints every problem, one per line, before exiting with code 1.
5. **Determinism.** Output depends only on the pinned input, the adapter config and `data/clubs.json`. Records are sorted by their key (`id`, or the composite key of `KEY_FIELDS`), object keys follow the schema order, JSON is written with two-space indentation and a final newline, and the result is stable under Prettier (`pnpm lint` checks `data/`). The clock is used only by the validator (`future-played-match`), never in the output. Running an adapter twice on the same input gives identical bytes; running it on its own output changes nothing.
6. **Club names.** Adapters resolve team names only through `resolveClubId` (ADR 0012: exact match after NFC normalization and trimming). Every unresolved name of the run is collected and reported together (sorted, with the first file and line where it appears), and the run fails; a name is never guessed and a match with an unknown club is never dropped silently. Within one season, two different source names that resolve to the same id also fail the run (ADR 0012, decision 3).
7. **Match ids.** A day-precision match id is `<date>-<home_id>-<away_id>` (for example `2024-05-10-sarmiento-junin-instituto`). It is source-neutral, so a later cross-check (API-Football for 2022 to 2024) computes the same id for the same match, and unique, because a club cannot play two matches on the same calendar day. A source that corrects a match date or swaps home and away produces a new id; that shows up as a removal plus an addition in the data PR, which is the intended review signal. Season-precision ids (Kaggle, ADR 0011) are defined by the Kaggle adapter's plan.
8. **Competition and season taxonomy (proposed, needs Diego).** A competition is a tournament that awards its own title; a season is one edition of it. The first adapter introduces:
   - `primera-division` ("Primera División", `league`, `domestic`, organizer `AFA`, `afa_recognized: true`): the main league tournament of each year. Season ids are `primera-division-<edition>`, where the edition is the year or split year (`2018-19`, `2021`), plus a suffix for split years (`2025-apertura`). Season `name` is the real Spanish name of the edition (`Superliga 2018-19`, `Liga Profesional 2024`, `Torneo Apertura 2025`).
   - `copa-de-la-liga-profesional` ("Copa de la Liga Profesional", `national_cup`, `domestic`, organizer `AFA`, `afa_recognized: true`), with season `copa-de-la-liga-profesional-2020` ("Copa Diego Armando Maradona 2020"). The Kaggle adapter reuses this id for 2021 to 2023.
   - Each competition's `source` is a permanent revision (`oldid`) of the Spanish Wikipedia article that states its organizer and AFA recognition. Season `start` and `end` are the first and last match dates of a complete source file (source: the file permalink); when the source file is known to be partial, the real end date comes from a cited source instead.

## Consequences

- A malformed upstream file, an unknown club or a conflicting reference record can never reach `data/`; the cost is that an ingestion stops until a person fixes the alias, the config or the data, which is the intended behavior.
- Ids of competitions, seasons and day-precision matches become a cross-adapter contract; the Kaggle and API-Football adapters must reuse them, and Supabase rows (plan 0006) key on them.
- Pinning upstream revisions means the data never changes on its own; picking up upstream corrections is a deliberate PR.
- Recorded fixtures of CC0 sources (openfootball) are committed under `tests/fixtures/ingest/`; sources whose terms do not allow redistribution (API-Football responses) must use reduced or synthetic fixtures, decided in their own plans.
- `data/` can only be written by an adapter run that passes the full validator, so the real data commit for openfootball also depends on every club of those seasons being present in `data/clubs.json` (issue #8 and #48).
- If Diego changes the taxonomy of decision 8, only the adapter config and this ADR change; the adapter code does not.
